Struct Vault

pub struct Vault { /* private fields */ }
Expand description

An open vault. Cheap to clone; clones share the same working copy.

Port of the TS AccountVault (plus the kdbxweb operations the web app runs on its db) and the Swift OpenedVault with the Database editing extensions.

pub async fn open_local( kdbx: Vec<u8>, credentials: KdbxCredentials, cancel: CancelToken, ) -> Result<Vault, OvError>

Opens a local .kdbx (not an account vault). TS decryptKdbx. vault_key_mismatch for a wrong password or key file (as TS 0.11 and [ov_kdbx::read] report it; contract-v1.7, was kdbx_error), kdbx_error for a damaged file, too_large for a key derivation over this build’s limits ([ov_kdbx::check_kdf_limits]), refused before it runs. Edits are stamped with the system clock (on wasm32, one second after the newest time in the file); OvClient::open_local uses the Host clock instead.

pub async fn create_local( name: String, credentials: KdbxCredentials, cancel: CancelToken, ) -> Result<Vault, OvError>

A new empty local database named name (KDBX 4, ChaCha20, Argon2id). TS createNewKdbx. OvClient::create_local does the same on the Host clock. It is saved as KDBX 4.0 until it holds something only KDBX 4.1 stores (an item’s previous group after a move or delete, tags on a group, …), then as 4.1, as KeePassXC 2.7 does (contract-v1.8).

pub async fn save_local(&self, cancel: CancelToken) -> Result<Vec<u8>, OvError>

Saves a local database with its credentials. invalid_request for an account vault (use sync). A KDBX 4.0 database that now holds something only KDBX 4.1 stores is written as 4.1 (contract-v1.8; KeePassXC 2.7 and later, and KeePass 2.48 and later, read every 4.1 element; older KDBX 4 readers open the file and drop them).

pub fn set_kdf(&self, kdf: KdbxKdf) -> Result<(), OvError>

Sets the key derivation a local database is saved with by save_local (a KDBX 3.1 file is upgraded to KDBX 4 for Argon2). invalid_request for an account vault, whose KDF belongs to its raw vault key; too_large over the limits a file is opened with ([ov_kdbx::check_kdf_limits]). Contract-v1.6.

pub fn copy_without_remotes( &self, credentials: Option<KdbxCredentials>, ) -> Result<Vault, OvError>

A separate local copy of this vault with its unsaved changes, without the sync-server and account-vault remotes in KeePassXC’s KPXC_REMOTE_SYNC_SETTINGS (command remotes stay): “Save a copy”, or “Export” of a whole database. It is saved with credentials, or a local file’s own credentials when None (invalid_request for an account vault or a version without credentials). A copy of an account vault (or of a version or SA vault) gets the KdbxKdf::DatabaseDefault KDF, since its vault KDF is only light because its key is random; change it with set_kdf. Contract-v1.6.

pub fn import_from( &self, source: Vault, mode: LocalImportMode, ) -> Result<ImportSummary, OvError>

Imports source (another open vault: a local file, an account vault, a version) into this one, without changing source. Its Recycle Bin stays behind. Database custom data (Meta/CustomData): with LocalImportMode::Merge the source’s items this vault doesn’t have are added (KeePassXC-Browser keys, for example), except its remote settings and the generated items (sync generation, _LAST_MODIFIED, KPXC_RANDOM_SLUG), and this vault’s own items are never changed (contract-v1.8; before, none came along); with LocalImportMode::Copies none come along, and references between the copied entries follow them. An account vault uploads the result on its next sync; a local file on save_local. Contract-v1.6.

pub async fn sync( &self, options: SyncOptions, cancel: CancelToken, ) -> Result<SyncReport, OvError>

Downloads, merges local edits and uploads them (conditional PUT; merge and retry on 412), SPEC §11, §13, §20. Offline, the working copy is kept on the device (encrypted) and uploads on a later sync; the error is network_error.

Edits made to this handle (or a clone) while the sync runs are kept (contract-v1.8; before, the sync’s result replaced them): the result is merged with them three ways, the copy the sync started from being the base, and they are uploaded in up to two more rounds of the same call (the first against the copy just uploaded, without downloading it again). Edits still landing after that, or when a later round can’t reach the server, stay in the working copy as unsynced edits (kept on the device like keep_edits; has_pending_edits) for the next sync, and the call still returns what the rounds that succeeded did: the report’s outcome is the most a round did (Created, then Uploaded, then Pulled), its conflicts, changes and attempts those of every round. Service-account vaults (write_field) work the same way.

The database custom data (Meta/CustomData) merges three ways too (contract-v1.8): an item added, changed or removed on one side since the last sync is taken, one changed on both keeps the newer copy’s value; before, an item another device added could be dropped.
